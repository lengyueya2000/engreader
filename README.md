# 阅见英语 · EngReader

一款面向**成人泛读提升**的 Android 英语阅读应用。抓取外刊全文后逐句精读，配合离线词库、朗读跟读、长难句拆解、理解自测与记忆曲线复习。

## 功能

| 模块 | 说明 |
| --- | --- |
| **划词查词** | 点单词弹出释义卡片：音标、词性分组的释义、考频分级、发音。点按偏移量由文本布局反查，点到标点不会误判 |
| **导入书籍** | 从手机里选 EPUB / MOBI / AZW3 / FB2 / HTML / TXT 整本导入，自动拆成章节存进本机，之后离线按章阅读。划词、翻译、朗读、长难句、自测对导入的书同样可用 |
| **全文查找** | 阅读页右上角的放大镜：在本篇或整本书里找词，命中处高亮显示并带上下文，点一条直接跳到那一段。输入停下 0.2 秒才查，逐字输入不会卡 |
| **阅读进度** | 退出再进来回到上次读到的段落，不用重新翻。换设备或重装后由"备份与恢复"带过去 |
| **备份与恢复** | 把生词本（含笔记、复习盒、语境原句）与阅读记录导出成一个 JSON 文件，换手机时导回去；按词条合并，重复导入不会产生重复数据 |
| **句子中文翻译** | 每句英文下方用小字附上对应的中文，逐句对照，可随时开关。首次打开某篇需联网获取，之后存在本机；内置选段的译文随包提供，离线也能看 |
| **多义消歧** | `found` 既是"建立"又是 `find` 的过去式，`left` 既是"左边的"又是 `leave`。按语料词频排序，主释义之外提供"另一种理解"一键切换 |
| **生词本** | 一键收藏，正文中已收藏的词带下划线高亮；支持搜索、按待复习/常错/已掌握筛选；每个词可写笔记，复习时一并显示 |
| **同族词** | 查词卡列出该词的其它形式（过去式、复数、派生词），点一下直接跳查；用词干回查词库补全 `exchange` 列没有收录的派生词 |
| **英英渐进** | 已经答对过的词，查词时先给英文释义，中文折叠在"看中文释义"后面；没答对过的词仍直接给中文 |
| **语境复习卡** | 查词时记下当时的原句，复习时先把该词挖空成"这句话里这个词是什么意思"，再对答案；答对后卡片附原文与笔记 |
| **个人生词率** | 按你的生词本算每篇"生词 N/M"与"轻松/合适/有挑战/偏难"判断，首页列表带 `生词 N 个` 角标；偏难时可先"预习生词"再读 |
| **记忆曲线复习** | Leitner 盒子（10 分钟 → 1 天 → 3 天 → 7 天 → 21 天），答对升盒、答错回退并当轮重现；卡片附同词性易混释义 |
| **朗读跟读** | 逐句朗读，正在朗读的句子高亮并始终留在屏幕上，点任意句子可跳转；语速与英/美口音可调，英式下另有纪录片解说音色与 BBC 解说大卫·爱登堡的克隆音色。语音随安装包提供，不依赖手机自带的朗读引擎 |
| **中英对照朗读** | 每句英文读完后接着用中文语音读出这句的中文，默认开启。读的是逐句对齐显示的那份译文，所以听到的和屏幕上看到的对得上；译文还没取回来、或这一段对不上时，这句只读英文。中文语音是第二个常驻引擎，中英交替不重新载入模型 |
| **后台朗读** | 锁屏或切到别的应用时朗读继续，通知栏与锁屏有播放控制（暂停/继续/停止），回来接着读；暂停后按播放从刚才那句开始，不是从头 |
| **长难句拆解** | 长按句子：先给"句子主干"，再按从句/非谓语/并列分句逐段拆解，标出主语谓语，并说明为什么这样理解 |
| **理解自测** | 从文章自身生成填空题与指代题，选项同词性同语域，答案可回溯原文 |
| **学习统计** | 每日目标、连续天数、14 天阅读柱状图、阅读速度（词/分钟）与前两周对比、生词难度构成、反复查的词 |
| **离线可用** | 内置 5.9 万词条词库（15 MB）与 8 篇公版分级选段（含预生成译文），无网络也能完整使用 |

## 内容来源

- **词库**：开源项目 [ECDICT](https://github.com/skywind3000/ECDICT)（含音标、中文释义、柯林斯星级、BNC/COCA 词频、考试标签），配合其 lemma 词形还原表
- **内置文章**：[Project Gutenberg](https://www.gutenberg.org) 公版文本选段（柯南·道尔、简·奥斯汀、达尔文、玛丽·雪莱、斯托克、威尔斯），译文在构建期生成
- **外刊全文**：各媒体公开发布的 RSS 与网页（卫报、BBC、纽约时报、经济学人），仅用于个人学习阅读。请求带 `If-None-Match` / `If-Modified-Since`，源站回 304 时直接用本机缓存，不重复下载正文；请求头声明 `Accept-Encoding: gzip`，响应按需解压
- **句子译文**：Google 翻译的公开接口，失败时降级到 MyMemory；需要网络，译文保存在本机
- **朗读语音**：[Piper](https://github.com/rhasspy/piper) 的 VITS 模型，用 [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) 推理。英式 `en_GB-alan-medium`（[mimic3-voices](https://github.com/MycroftAI/mimic3-voices) 的 apope 录音）、美式 `en_US-lessac-medium`（LibriTTS/Blizzard 系公开录音）、纪录片解说音色来自 [VCTK](https://datashare.ed.ac.uk/handle/10283/3443) 语料的 p274 说话人（CC BY 4.0）。音素化用 espeak-ng 的英语数据
- **爱登堡克隆音色**：[ZipVoice](https://github.com/k2-fsa/ZipVoice)（Apache-2.0）的 int8 量化包，取自 [sherpa-onnx 发布的 tts-models](https://github.com/k2-fsa/sherpa-onnx/releases/tag/tts-models)，声码器是同一发布页的 `vocos_24khz.onnx`。参考录音取自 [Penguin Audiobooks 官方发布的《A Life on Our Planet》有声书试听](https://www.youtube.com/watch?v=OTxufJJCoTM)（爱登堡本人朗读自己的书），剪辑与逐字校对由 `tools/voice/pick_reference.py` 与 `tools/voice/measure_bandwidth.py` 完成。**这段录音是本人声音，权利属于他本人与录制方**，此处仅用于个人学习阅读；商用分发需要另行取得授权
- **中文朗读语音**：Piper 的 `zh_CN-xiao_ya-medium`（小雅，22.05 kHz），取自 [sherpa-onnx 发布的 int8 量化包](https://github.com/k2-fsa/sherpa-onnx/releases/tag/tts-models)。它不走 espeak-ng，而是用同一个包里带的拼音词典与三条规则 FST（日期、数字、电话号码）做前端——书面数字得先转成拼音，词典才查得到。训练语料是 [BZNSYP](https://huggingface.co/openspeech/BZNSYP)（Data Baker 标准中文女声），该语料**仅限非商业用途**

## 导入书籍

首页右上角的加号选一个文件，整本书会被拆成章节写进本机数据库，之后不联网也能读。格式按**文件内容**判断，不看扩展名：认不出就明确拒绝，不会把乱码当正文存进来。

| 格式 | 容器 | 正文压缩 |
| --- | --- | --- |
| EPUB | zip + OPF manifest/spine | 直接是 XHTML |
| MOBI | PalmDB + PalmDOC header | 不压缩 / PalmDOC LZ77 / HUFF-CDIC |
| AZW3 (KF8) | 同上，MOBI header version ≥ 8 | 同上，正文按 FDST 分片裁剪 |
| FB2 | 单个 XML 文件 | 无 |
| HTML | 单页或 `index.html` + 同目录页 | 无 |
| TXT | 纯文本 | 无 |

纯文本没有目录，所以章节从正文里认：先试项目 Gutenberg 那种 `CHAPTER II.`，再试光秃秃的罗马数字或阿拉伯数字（`XII`、`3`）。章节号拼写出来的也算（`Chapter One: The Beginning`）——但要跟"句子里正好提到 chapter"区分开，所以标记必须在短行开头。一个章节标记都没有的长文本会按段落边界切成约 6000 词一节，免得整本书被当成一章、进阅读器前先把全文切成句子。编码先按 BOM 判，再试 UTF-8，失败退回 GB18030（老中文 txt 常见），不会整篇变成替换字符。

解析器是纯 JVM 的（`book/` 目录不碰 Android SDK），所以 `app/src/test/` 能直接对着真实文件跑：仓库里的合成 fixture 覆盖每种压缩方式与错误路径，另有 4 个用例对着 25 MB 的《傲慢与偏见》EPUB / MOBI / AZW3 跑（用 `-Pengreader.bookFixtures=<目录>` 指定书所在目录，没有就跳过）。

设计上有一个决定值得说明：**一章就是一条普通的 `article` 行**，只是多了 `bookId` / `chapterIndex` 两个字段。因此阅读器、词库、语法面板、自测、朗读全都不需要为书写一份分支——书和文章的差别只剩"有没有下一章"。反过来，`ArticleRepository.recent()/saved()/all()` 会过滤 `bookId = 0`，一本小说不会把首页的文章列表冲掉。

目录标签是脏活。同一本《傲慢与偏见》，三个格式给出三种东西：EPUB 的 NCX 里每章写的是 `I hope Mr. Bingley will like it. CHAPTER II.`（插图的说明文字加章节号），MOBI 把 `CHAPTER II.` 排成一个居中段落而不是 `<h2>`，AZW3 又换了一套。所以标签的取法是有序降级：真实标题（`<h1>`–`<h3>`）优先，其次在章节开头 400 字符里找章节标记，标记前若是 `Heading to` / `Tailpiece to` 这类插图说明则跳过。反过来，导航文档里带的标签也会被同样清理，`... CHAPTER II.` 只留 `CHAPTER II`。这一条有单测，因为靠肉眼在七十条目录里发现问题并不现实。

正文换行也踩过一次坑：转换过的书把段落按 72 列硬换行，所以一个段落横跨多行源码。如果按源码换行切段，一句话会被切成两半，阅读器里段落碎掉、语法拆解拿到的是残句。现在的做法是先把块级标签替换成一个哨兵字符，再把所有空白（含源码换行）压平，最后按哨兵分段——段落的边界只来自标签，不来自排版。

## 正文提取

外刊正文由 `source/Html` + `source/ArticleExtractor` 提取，站点无关：收集所有 `<p>`，剔掉 chrome（图注、署名、cookie 与订阅文案、相关阅读），留下读起来像散文的段落。这一段被 20 篇真实页面（卫报 12 + BBC 8）对拍过，改动的规则都能在这批页面上看出差别。

**去标签分两类。** 块级元素（`p`、`div`、`br`、`li`…）边界处换成空格，行内元素（`a`、`em`、`span`…）直接删掉。早先的规则是"每个标签都换成空格"，于是 `<a …>Gaza</a>.` 到读者眼里成了 `Gaza .`——一个句子里的链接或强调会把它后面的标点从词上拽下来。删除行内标签也正是浏览器的做法：两个行内元素之间没有空白，屏幕上就没有空格。

**标点旁的多余空格会收拢。** 有的页面把空格写进标签（`word <em>,</em>`），`&nbsp;` 解码后也是一个空格，两者都会留下英文里不该有的间隙，所以 `,.;:!?%` 与右引号、右括号前的空格、左引号与左括号后的空格会被收掉。方向不明确的字符不动：`'` 和 `"` 开合都有可能，破折号两侧加空格是卫报的体例，省略号前的空格是正常英文。

**几类假段落要单独认出来。** BBC 用 `visually-hidden` 的 class 藏辅助阅读文字，其中 `, external` 跟在每个外链后面，会把一个已结束的句子变成 `…in a post on X., external`；图注和页脚都是普通 `<p>` 写的，页脚因此变成正文最后一段"Copyright © 2026 BBC…"，图注变成插在散文中间的孤立句子；"延伸阅读"卡片也是普通 `<p>`，只是整段被 `<a>` 包住，长度过滤拦不住。现在这三类分别按 class、按容器（`figure`/`figcaption`/`footer`）和按链接范围剔除。

**标签里的 `>` 不能提前结束标签。** 早先的属性部分写成 `[^>]*`，遇到 `title="5 > 3"` 这种合法写法就在引号内的 `>` 处收尾，于是标签没被匹配、`3">alpha` 漏进正文。现在引号内的一整段被当作整体跳过，`>` 只有在引号外才算标签结束。同理，没有 `<p>` 可用的页面会回退到"块级容器之间的最长文本块"，取块用的是深度计数而不是惰性正则——`<div><div>a</div>b</div>` 以前只拿到 `a`，`b` 被丢掉。

**命名空间前缀要剥掉。** RSS 解析器不处理命名空间，拿到的元素名是带前缀的 QName；直接和 `content`、`date` 比较，等于把 `media:content`、`media:thumbnail`、`dc:date` 全部丢掉——线上目录源里这些元素是配图与日期的唯一来源。

## 朗读语音

语音模型在安装包里，不读设备上的系统 TTS——同一个应用在不同手机上会得到完全不同的音色，有的手机甚至没有英语语音包，而"听文章"是这个应用的主要功能之一。

**朗读时界面跟着句子走，而不是跟着段落走。** 早先的自动滚动只把"正在朗读的那一段"滚到顶部，可小说里一段常比一屏还高，句子的首行对齐了顶端，正在读的那句却在折叠线以下，读着读着就滑出屏幕底部，越读越看不到。现在每句话在屏幕上占的矩形都上报给滚动逻辑（`ReaderScreen.kt` 里的 `SpokenBounds`），只有当前朗读句跑出上下的留白带时才轻推一下列表：带内不动，出带才对齐——每句都滚会把页面从读者眼前拽走。句子的矩形用 `positionInWindow` 自己算，不用 `boundsInWindow`，因为后者会被窗口裁掉：刚滚出底边的句子会报成空矩形，和"还没被合成"长得一模一样，滚动就再也发现不了它要追的那句已经出屏了。

| 口音 | 音色 | 模型 | 说明 |
| --- | --- | --- | --- |
| 英式 | Alan | `en_GB-alan-medium` | 标准朗读，男声 |
| 英式 | Narrator | `en_GB-vctk-medium` p274 | 纪录片解说，男声 |
| 英式 | 爱登堡 | `en_GB-attenborough` | BBC 纪录片解说，**克隆音色**，男声，24 kHz |
| 美式 | Lessac | `en_US-lessac-medium` | 标准朗读，女声 |

前三个里只有最后一个是**真的**大卫·爱登堡——它和另外三个不是同一种东西。另外三个是训练好的图里的某个说话人，换不了人；爱登堡这一条是 [ZipVoice](https://github.com/k2-fsa/ZipVoice) 零样本克隆：模型本身与说话人无关，音色来自随包的一段 6.8 秒参考录音，合成时把那段录音的嗓音复制过来。参考录音取自 Penguin Audiobooks 官方发布的《A Life on Our Planet》有声书试听，与逐字校对后的文本一起放在 `app/src/main/assets/tts/en_GB-attenborough/reference.wav` 和 `reference.txt`。

**参考音频的音质直接决定克隆出来的清晰度。** 这是第一版翻车换来的结论：当时那段参考取自一个第三方数据集，听者反馈"像含着东西说话"。量出来问题不在带宽（硬截止 11.6 kHz，和替换版基本一样），而在**噪声底**——帧信噪比只有 16.6 dB，替换后的官方录音是 34.4 dB。零样本克隆把录音通道连同音色一起复制，所以参考里的闷和噪会出现在每一句里。用同一批句子分别以两段参考合成，输出 4 kHz 以上能量约 +3.5 dB、信噪比约 +2.8 dB，可懂度（WER）本来就都合格、基本不变。判据与测量脚本在 `tools/voice/measure_bandwidth.py`，里面还写清了哪些指标**不能**用来判：`r20`、4-8k 能量这些数受"这句话里有多少擦音"支配，同一批次里换个句子就能差 4 dB，拿它们设门槛会把好片段判死。

**参考音频必须和它的文本逐字对应。** ZipVoice 把音频和文本对齐着学音色，喂进去一个对不上的文本，它照样出声，但音色会飘——那听起来像"有点怪"，不像一个 bug。所以每一段参考都是用 `faster-whisper` 带词时间戳转写后**从词边界生成文本**的（两个模型交叉核对一致），不是手抄的。第一版就是因为切点压在词中间，转写多出一个 "it"，文本里却没有——这种错位不会报错，只会让音色发虚。同理不能为了省合成时间把参考剪短：实测把 8 秒参考截到 2.5 秒，合成确实快了四倍，但文本与音频不再对应，十二句的 WER 从 0.05 崩到 0.86。

**参考的长度同时也是每一句的合成成本。** 克隆音色每次调用都要重新编码这段参考，所以它比 Piper 音色多一项固定开销；6.8 秒是"够认音色"和"别让引擎追不上播放"之间量出来的折中（见下文停顿一节）。

`num_steps` 取 4：这是**说话人身份**这条底线之上最省的一档。2/4/6 步的合成耗时分别是实时的 0.21/0.39/0.54 倍，而用 ECAPA-TDNN 给合成结果做声纹比对（拿几段确认是本人的录音定下同人下界 0.768），2 步只有 0.753、**掉到下界以下**——那就不是他的声音了；4 步 0.789 通过，WER 也从 0.092 降到 0.061。省一半算力换丢音色，是笔亏账。

> 这里要更正一段旧文字：本文早先是用 MFCC 统计距离论证 4 步的（"4/8/16/32 步 0.56/0.49/0.54/0.56"）。那个测量不可信——同样的输入重跑，波动比它想分辨的差别还大，而且对步数不单调。声纹要用为声纹训练的模型来判，`tools/voice/` 里换成 ECAPA 之后结论才站得住。


**Narrator 那一条的历史依据。** 在爱登堡这一条加进来之前，公开可用的 Piper / VITS 语音都是在 VCTK、LibriVox、OpenSLR 这类公开语料上训练的，没有任何一个是拿真人解说员的录音训出来的——那是声音克隆，需要本人授权。所以当时能做的是从公开语料里挑出**听感最接近纪录片解说**的说话人：从 VCTK 的 109 个说话人里，先按语料自带的 `speaker-info.txt` 排除苏格兰、爱尔兰、威尔士、北爱尔兰、印度与美国口音（这些不是"英音"），剩下 15 个英格兰男声，再按可测量的朗读特征排序。下表每个数字都是 5 次合成的平均值，`±` 是标准差：

| 说话人 | 中位基频 | 语速 | 停顿次数 | 音高跨度 | 语料标注 |
| --- | --- | --- | --- | --- | --- |
| Alan（原有） | 93.3 ±0.2 | 179 ±1.2 | 11.6 ±1.0 | 1.88 ±0.07 | 单说话人 |
| **p274（选中）** | 100.0 ±0.6 | 208 ±2.9 | **6.4 ±2.2** | 3.19 ±0.16 | 22 岁，Essex |
| p287 | 99.9 ±0.5 | 239 ±5.8 | 0.2 ±0.4 | **4.02 ±0.25** | 23 岁，York |
| p226 | 112.7 ±0.6 | 219 ±2.4 | 1.6 ±1.7 | 3.32 ±0.10 | 22 岁，Surrey |
| p254 | 82.3 ±0.6 | 244 ±9.2 | 0.2 ±0.4 | 7.49 ±8.6 | 21 岁，Surrey |

选 p274 的理由是它**在从句之间真的停下来**，而且语速最接近解说（208 wpm，原有 Alan 是 179）。p287 的音高跨度更大，但语速 239 wpm、几乎不停顿，听感更接近播报；p254 的音高跨度看着最高，但 5 次之间从 3 跳到 20 半音，这个数字本身不稳定，不能作为依据。

两点必须说明，否则上面的表会被误读：

- **VITS 每次合成都带随机噪声，单次测量会骗人。** 最初一版按单次结果排序，把 p274 的停顿数读成 2；5 次平均后是 6.4。基频和音高跨度的重复性很好（±0.6 Hz、±0.16 半音），停顿数与语速的波动则和说话人之间的差距同量级，所以排序以基频和音高跨度为主，停顿与语速只作参考。
- **口音判断用的是语料自己的标注，不是声学测量。** 试过用 TRAP–BATH 元音的前两个共振峰来分辨南方英音，但在 200–400 ms 的合成词上 LPC 估计会在两次运行之间翻转符号，那等于抛硬币。苏格兰/爱尔兰/威尔士这类区分，语料标注是可靠的，声学推断不是。

测量脚本在 `tools/voice/measure.py`，换语料重新挑人时可以跑：

```bash
python tools/voice/measure.py \
  --single alan=<解包后的 en_GB-alan-medium 目录> \
  --vctk <解包后的 en_GB-vctk-medium 目录> \
  --espeak <任一语音包里的 espeak-ng-data> \
  --sheet speaker-info.txt --english-only
```

**句子边界是朗读的最小单位，切错就等于在句子中间落了一个句号。** 朗读按句合成（见下文"句间停顿"），所以 `Sentences.split` 切在哪里，语音就在哪里走一遍句末语调并重新起头。原来的规则只在句点后面看下一个词是不是小写，收尾引号、叹号、问号、省略号一概不看：`“Do not you want to know who has taken it?” cried his wife, impatiently.` 被切成两句，第二句 `cried his wife, impatiently.` 单独合成，听感就是说到一半先落一个句号。现在句号以外的终止符、以及跟在收尾引号后面的情况，都按同一条规则处理——下一个词小写或数字就还在同一句里（`?” cried his wife`、`“How so? how can it affect them?”`），大写才是新句子（`He said “stop.” Then he left.`）。把 `tools/raw/pg1342.txt` 这类真实文本整段拼起来逐句切，改前有 4 句是被切出来的半句，改后为 0。

### 克隆音色（爱登堡）

爱登堡这一条走的是另一条通路，和上面三个 Piper 音色不共用任何代码路径。

**它不是"图里的第几个说话人"，而是一段录音。** ZipVoice 是说话人无关的模型：文本编码器把句子编成特征，流匹配解码器把特征变成梅尔频谱，声码器把频谱变回波形——三张图里都没有音色。音色来自每次合成时一并传进去的参考音频与它的文本（`GenerationConfig.referenceAudio` / `referenceText`），模型把这段录音的嗓音对齐着复制过来。所以它比其他音色多两个必需文件，少一个可选字段（没有 `sid` 可言）。

**三条路径都必须按相对路径从 APK 里读。** 和中文那边同一个理由：绝对路径 + `AssetManager` 会让原生库直接结束进程。三张图（`encoder.onnx` 119 MB、`decoder.onnx` 5 MB、`vocoder.onnx` 52 MB 中的解码器部分）与字符词典都留在 APK 内，一个字都不解包；唯一落盘的仍是 espeak-ng 数据——ZipVoice 自带字符词典，但词典里没有的字母仍要 espeak 兜底，所以它同时需要 `lexicon` 和 `dataDir`。

**声码器不能和别的模型混用，混错了不会报错。** ZipVoice 的梅尔是 100 维、24 kHz，官方发布的 `vocos_24khz.onnx` 是唯一对得上的那个；`vocos-22khz-univ.onnx` 是 80 维，喂进去会报 `Got invalid dimensions for input: mels ... Got: 100 Expected: 80`，而 HiFiGAN 那几个虽然能加载，输出却是噪声。试过用 3.6 MB 的 `hifigan_v2.onnx` 替掉 52 MB 的声码器来省体积，架构不兼容，只能作罢。每个克隆音色因此自带一份声码器，不共用。

**参考音频对不上文本会飘，不是会坏。** 解析 WAV 的 `VoicePrompt` 只在两种格式上工作：16 位 PCM 与 32 位浮点，单声道。别的格式一律拒绝并把音色报成不可用——因为按错误的位宽解出来的样本是噪声，而噪声会被归咎于模型。这个类有一个 16 位样本的符号扩展 bug 被单测抓到过：`00 80` 按无符号拼出来是 32768，除以 32768 得 +1.0，本该最轻的样本变成了最响的一声爆音。

### 中英对照朗读

打开「英文后接着朗读中文」（默认开）后，每句英文读完会紧接着读这句的中文。读的不是另取的一份译文，而是**屏幕上逐句对照显示的那一份**——同一次 `SentenceAlignment.align` 的结果，所以听到的和看到的对得上；译文还没取回来、或这一段机器翻译改写得太厉害对不上时，这一句只读英文，不会停下来等。

**两个模型同时驻留内存。** 中英是一句一交替的，如果每对之间都换一次模型，一对句子里就会插进约一秒的空白；而两个引擎各占约 19 MB 的图，换来的代价比这点内存更贵。所以英文一个引擎、中文一个引擎，各自 `@Volatile` 一个槽位，切句只是换槽位，不重新载入。中文引擎在打开文章时就后台开始载入，正好和"读者还在看文章"的时间重叠，而不是和第一句的朗读重叠。

**中文不走 espeak-ng。** sherpa-onnx 的 Piper 通路把 espeak 的语音名硬编码成 `en-us`，`OfflineTtsVitsModelConfig` 也没有暴露语音名的字段——原生库里既搜不到 `cmn`，也没有设置语音名的入口——所以中文模型走 espeak 会被英语规则音素化。`zh_CN-xiao_ya-medium` 的解法是自带拼音词典：模型配置里 `phoneme_type` 是 `pinyin`，引擎按字查词典得到声母韵母和声调，再用三条规则 FST 把书面数字改写成拼音能读的形式（`1837` → `一八三七`），这正是英语那边 `SpokenText` 手工做的事的中文对应物。两条前端互斥，不能共用一个引擎。

**所有路径都必须是 APK 内的相对路径。** sherpa-onnx 把这两种模式当成互斥的：设置了 `AssetManager` 却给了绝对路径，它只打印一句 `you are using an absolute path ... but assetManager is NOT set to null` 然后**直接结束进程**——不是异常，`runCatching` 接不住。第一版把拼音词典解包到 `filesDir` 再传绝对路径，点开文章就闪退。现在模型、tokens、词典、三个 FST 全部按相对路径从 APK 里读，一个字都不用解包（espeak-ng 的数据是唯一例外，它用 `fopen` 自己开文件，必须落盘）。

**中文读失败不会中断朗读。** 英语语音是主体，中文是附加的，所以中文引擎缺失、载入失败或合成不出音频时，队列把这一句当作"已读完"直接进下一句英文；而英语那边失败仍然按原来的语义停止朗读——"语音没了"和"这句没译文"是两件事。

代价是安装包每个 ABI 增加约 13.8 MB（中文模型 int8 后 18.6 MB，在 APK 里压到约 13.8 MB），朗读时多常驻一个约 19 MB 的引擎。相对于英语语音已有的约 60 MB，这是把功能做完整所必需的。

### 朗读前把书面语改写成人话

内置语音是拿 espeak-ng 做音素化的，它读数字和符号用的是通用朗读规则，不是"有人在念小说"的规则。实测（用同一套内置语音合成、再用 faster-whisper 回听识别）发现四处一听就知道是机器在念的地方，朗读前统一改写：

| 原文 | 直接读出来 | 改写后 |
| --- | --- | --- |
| `1837`（句中出现） | one thousand eight hundred and thirty-seven（整句 6.85 秒） | eighteen thirty-seven（整句 5.22 秒） |
| `CHAPTER VI.` | chapter vee eye | Chapter six |
| `8:35 P. M.` | eight thirty-five p, M | eight thirty-five p m |
| `[Illustration: …]` | 整条注释当作正文念（句内多出 6.3 秒；单独成句时 7.2 秒） | 不念 |
| `it was **very** important and _quite_ true` | 每个星号都念成 asterisk（5.17 秒） | it was very important and quite true（2.69 秒） |

年份只在**时间语境**里改写：前面是 `in`、`since`、`by`、`copyright` 这类词，或者紧挨着另一个年份时才当作年份，`1234 people` 这种数量照旧读数字。`1837-1901` 这样的年份区间不改——语音本来就会把连字符读成 "to"，改了反而多一道错的机会。罗马数字也只在章节标题、君王名（`Henry VIII`）、卷次这些位置改写，而且要求它能严格往返转换（`X` 是 10，但 `IIII` 不是合法写法，就不动）；单独的 `I` 是代词，不碰。

**故意不改的是连读本身。** 先量了再说：同一句话里把 `to` 换成拼写不同的 `two`，8 次合成的均值是 1.101 秒对 1.260 秒（标准差各 0.03，差距约 5 个标准差）——弱读已经在发生，改写它反而是错的。对 "It is a truth universally acknowledged, that a single man" 做逐词时间戳，短语内部的词间空隙全是 0.000 秒，整句唯一的一段停顿是逗号处的 0.700 秒：该连的地方已经在连。缩写（`Mr.`、`Mrs.`、`Dr.`）、`It's` 这类缩合、`8:35`、`5 p.m.` 同样已经正确，写规则去"修"它们只会多一个出错的途径。

上面这些数字都可以用 `tools/voice/say.py` 重新量一遍（默认模式回听识别，`--duration` 比较改写前后的音频长度，`--words` 打印逐词时间戳）。

改写只发生在交给语音引擎的那一份文本上，界面上的原文一个字都不动，所以高亮位置和点击划词都还指向原句。整条注释独占一句时（Gutenberg 版的 `[Illustration: …]` 就是单独一行），改写结果可以是空字符串，此时朗读队列直接跳到下一句——实测这条注释是 7.2 秒的音频，没有听众想要它。

规则都写在 `app/src/main/java/com/engreader/app/tts/SpokenText.kt`，每条边界都有对应的测试（`SpokenTextTest`），另有一份把应用自带的 58 段正文冻结成语料的回归测试（`SpokenCorpusTest`），保证改写既不会丢词，也不会突然开始改写本来不需要动的段落。

## 构建

环境要求：JDK 17+、Android SDK（platform 35、build-tools 35）、Gradle 8.9。

```bash
# 首次需要生成数据资产（已生成则可跳过）
python tools/build_dict.py          # -> app/src/main/assets/dict.db
python tools/build_seed.py          # -> app/src/main/assets/seed_articles.json
python tools/build_translations.py  # 为内置选段补中文译文（写回同一文件）

# 首次需要取爱登堡克隆音色的模型（186 MB，不进 git，见下文）
python tools/voice/fetch_attenborough.py

# 构建
./gradlew :app:assembleDebug      # 调试包（每个 ABI 一个）
./gradlew :app:testDebugUnitTest  # 单元测试
./gradlew :app:assembleRelease    # 发布包（需 keystore.properties）

# 拿真实电子书跑解析器的单测（可选，没有就跳过这些用例）
./gradlew :app:testDebugUnitTest -Pengreader.bookFixtures=/path/to/books
```

语音模型与 sherpa-onnx 引擎无需额外下载：四个 Piper 音色在 `app/src/main/assets/tts/`，引擎是 `app/libs/sherpa-onnx.aar`（sherpa-onnx 没有 Maven 产物，因此随仓库提供）。构建按 ABI 拆包，`arm64-v8a` 给真机、`x86_64` 给模拟器；`armeabi-v7a` 与 `x86` 被排除，因为语音模型共约 250 MB，32 位进程放不下。**发布的 Release 只带 `arm64-v8a`**，`x86_64` 包只用于模拟器调试。

爱登堡克隆音色的 186 MB 模型（`decoder.onnx` 124.7 MB、`vocoder.onnx` 54.2 MB、`encoder.onnx` 5.6 MB、`lexicon.txt` 1.7 MB、`tokens.txt`）**不在仓库里**：GitHub 拒绝单文件超过 100 MB 的推送。它们放在本项目的 Release 资产里，用 `tools/voice/fetch_attenborough.py` 下载安装，脚本会逐文件核对 SHA-256——模型被换掉的话，克隆出来就是另一个人的声音，而 App 无法分辨，所以这里宁可拒绝也不要装。参考录音 `reference.wav` / `reference.txt` 只有 326 KB，随仓库提交。

`tools/build_dict.py` 与 `tools/build_seed.py` 需要把原始数据放在 `tools/raw/`（该目录已 git-ignore）：`ecdict.csv`、`lemma.en.txt` 来自 ECDICT 仓库，`pg*.txt` 来自 Project Gutenberg。
`build_translations.py` 只处理内置选段（8 篇、约 70 段），需要网络；外刊译文由 App 在运行时按需获取。

`tools/book/` 下的两个脚本是解析器的对拍工具：`reference_mobi.py` 是一份独立的 Python MOBI 解压实现，用来给 Kotlin 端口产出期望值；`build_fixtures.py` 生成 `app/src/test/resources/book/` 里的合成 fixture（每种压缩方式、尾随条目、加密、截断各一份）。改动 MOBI 解析后先跑一遍单测，比对着真书肉眼检查快得多。

### 发布签名

`keystore.properties` 与 `*.jks` 不入库。本地生成：

```bash
keytool -genkeypair -v -keystore engreader-release.jks -alias engreader \
  -keyalg RSA -keysize 2048 -validity 10950 \
  -dname "CN=EngReader, O=EngReader, C=CN"
```

然后写 `keystore.properties`：

```properties
storeFile=engreader-release.jks
storePassword=...
keyAlias=engreader
keyPassword=...
```

缺这个文件时 release 包会构建为未签名版本，而不是让构建失败。

```
│   ├── SentenceAlignment   把整段译文切回逐句；句数一致直接用，不一致按比例分配
│   └── MiniJson            纯 JVM JSON 解析，供响应解析与单测
├── tts/            内置神经语音（模型随包 + 逐句队列 + 完成回调）
│   ├── Speech.kt       语音目录：口音分组、音色、引擎类型、模型/克隆路径、拼音词典与规则 FST 路径
│   ├── VoicePrompt.kt  克隆音色的参考音频：WAV 解析（16 位 PCM / 32 位浮点，单声道）与文本配对
│   ├── NeuralTts.kt    sherpa-onnx 推理（合成线程）+ AudioTrack 播放（播放线程）+ 下一句预合成；英文、中文各一个常驻引擎，Piper 与 ZipVoice 两条通路
│   ├── Speaker.kt      后端路由：内置语音优先，系统 TTS 仅作降级；按角色分派中英文
│   └── PlaybackService.kt  前台服务 + MediaSession：锁屏与通知栏的播放控制
└── ui/             Compose 界面
```

分析层（`nlp/`、`dict/`、`translate/`）不依赖 Android SDK，因此可以在 JVM 单元测试里直接跑——`app/src/test/` 覆盖了句子切分、语法拆解、出题逻辑与译文解析。`tts/Speech.kt` 同样不碰 Android，语音目录的解析规则也在单测里；`ChineseVoiceAssetsTest` 另外盯着随包的中文前端（六个文件都在、词典是拼音的、路径全是相对路径）。

逐句对齐另有真书语料：`app/src/test/resources/translate/alignment_corpus.tsv` 是《傲慢与偏见》七十个多句段落的英文与**在线接口实际返回的**中文，`AlignmentCorpusTest` 用它守住"至少九成段落能逐句对照"与"句内误切不超过 12 处"两条线。手写的用例可以被调参调到刚好通过，真书语料不行——换算法、改阈值，掉多少个百分点、多切错几处，这里看得见。语料上精确句数匹配只覆盖 62% 的段落，比例分配把可逐句对照的段落补到 100%。

## 数据库

用户数据在本机 SQLite（`engreader.db`），当前 schema 版本 **5**。

| 表 | 内容 |
| --- | --- |
| `article` | 抓取与内置的文章，以及导入书籍的章节（`bookId > 0`）；`wordCount` 是该篇的词数，`vocabProfile` 缓存该篇的实词表（换行分隔），换设备重算即可；`readParagraph` 是上次读到的段落序号 |
| `book` | 导入的书：标题、作者、格式、原文件名、封面文件名、章节数、阅读进度与累计时长 |
| `word` | 生词本：Leitner 盒号、到期时间、正确/错误次数、个人笔记 |
| `lookup` | 每次查词；`sentence`/`surface` 记下当时的原句与词形，供复习卡还原语境 |
| `session` | 每次离开阅读器或切到后台写入一条，用于时长、连续天数与阅读速度。`wordsRead` 是**当时读到哪儿**对应的词数（覆盖量），不是这一段的增量，所以同一次阅读会留下多行、词数相同，统计时按文章取最大值 |
| `quiz` | 自测成绩 |

升级走 `onUpgrade` 里的 `ALTER TABLE`，不清表：v1 → v2 给 `lookup` 加 `sentence`/`surface`、给 `article` 加 `vocabProfile` 并建 `idx_lookup_lemma`；v2 → v3 给 `article` 加 `bookId`/`chapterIndex`（默认 0，所以旧文章自动都是"非书籍"）、建 `book` 表与 `idx_article_book`；v3 → v4 给 `article` 加 `wordCount` 并回填旧行（按正文现算，不再靠"空格个数"估）、给 `session`/`quiz` 的 `articleId` 建索引；v4 → v5 给 `article` 加 `readParagraph`（默认 0，旧文章的阅读进度就是开头）。每条语句前都查一次 `PRAGMA table_info`，所以中途失败后重跑是安全的。早期版本直接 drop 重建，在只有测试数据时无所谓，但会连生词本和阅读历史一起清掉。

**备份与恢复**（设置页）导出/导入一个 JSON 文件，只含用户数据——生词本与阅读记录，不含正文与语音。导入是一个事务：生词按 lemma 合并（新词插入，已有的只在备份盒号更高时覆盖，笔记空则不覆盖），`session` 按 `articleId + finishedAt` 去重，所以重复导入同一份文件不会翻倍。文件带 `format` 与 `version` 两个字段，认不出或版本更高的文件会被拒绝并说明原因，不会写进半截数据。

导入一本书是**一个事务**：书行、封面文件与全部章节一起提交，中途失败则整体回滚并删掉已落盘的封面，不会留下"架上有书、点开没章节"的空壳。删除一本书同时清掉它各章的 `session` 与 `quiz` 行。

## 设计

- **配色**：暖纸色底（`#FAF8F3`）+ 松绿主色（`#1F5A4A`）+ 琥珀强调，正文衬线、界面无衬线
- **阅读底色**独立于应用主题：纸白 / 米黄 / 夜间三选一，顶栏与操作按钮跟随阅读底色

## 已知限制

- **朗读不依赖系统 TTS**：语音模型随安装包提供（英式三个、美式一个，加中文一个），任何设备上音色一致，模拟器上也能出声。代价是安装包变大，且按 ABI 拆包：1.8.0 的 `arm64-v8a` 发布包 256 MB、`x86_64` 259 MB（后者只用于模拟器调试，Release 只发 arm64）。sherpa-onnx 的原生库每个架构约 24 MB，Piper 语音约 77 MB，爱登堡克隆音色另加约 186 MB，三者都压不下去。只有在内置模型载入失败时才会退回系统朗读引擎，此时音色由设备决定
- **爱登堡音色是真人克隆，且它让安装包大了两倍多**：这一条和别的音色不是一回事。它是 ZipVoice 零样本克隆，参考录音是爱登堡本人的公开广播音频——**声音的权利属于他本人与录制方**，这里按个人学习用途使用；要商用分发得另行取得授权，跟中文语音那条 BZNSYP 的限制是同类问题。体积上，ZipVoice 的解码器 124.7 MB、声码器 54.2 MB、文本编码器 5.6 MB、词典 1.7 MB，共 186 MB，比另外四个音色加起来还大一倍；换成 3.6 MB 的 HiFiGAN 声码器试过，架构不兼容只能作罢。这 186 MB 不在仓库里（GitHub 不收超过 100 MB 的单文件），见上文"构建"里的取用步骤。速度上，桌面 CPU 逐句合成约 0.32 倍实时（最慢一句 0.38），手机更接近实时——靠 `prefetch` 预合成后面几句把这部分耗时藏起来，藏不掉的部分见下文"句间停顿"。装载要等更久，而且是**每个进程一次**：首次选中该音色会把 186 MB 读进内存并建三个 ONNX 图，实测冷态 40 秒、热态不到 1 秒（模拟器 4 核 x86_64），真机上十几到二十几秒——其中解压只占 0.7 秒（271 MB/s），其余是建图。所以"等语音就绪"的窗口**按音色给**：Piper 15 秒，克隆音色 90 秒（`VoiceCatalog.CLONING_LOAD_WAIT_MS`）。原先这里只有一个值，且它自己的注释写着是照 19 MB 的 Piper 图定的，套到 186 MB 上就会把"还在正常加载"判成"这个音色不可用"，进而静默中断朗读——真机上"选了爱登堡、点朗读没声也没报错"就是这么来的。它合成出来的停顿处还有一层静止的全频嘶声：同文本对照（n=12，克隆朗读本人那段原话再与其录音比对），比本人录音的房间底噪高 `floor_p05` **6.76 dB**、`pause_rms` **7.11 dB**（12/12 与 11/12 同号，9 种帧长×阈值组合下稳健），频谱质心 2438 Hz 对房间的 522 Hz。播放前过一道噪声门（−45 dBFS 阈值、最多 −20 dB、80 ms 释放）把这层压低 7–10 dB，而语音只掉 0.3–0.5 dB；其余四个音色的底噪从未测过，所以不门——凭信心改没测过的东西，仍然是改
- **中英对照朗读要多占一个引擎**：打开后中文语音与英文语音同时常驻内存（各约 19 MB 的图），换来的是中英交替时不重新载入模型。中文这一侧读失败只跳过这一句，不会中断朗读；关掉开关后中文引擎仍留在内存里直到朗读会话结束，重新打开不需要再等载入
- **中文语音的语料仅限非商业使用**：`zh_CN-xiao_ya-medium` 训练自 BZNSYP（Data Baker 标准中文女声），该语料标注的授权是"仅限非商业用途"（见上文"内容来源"）。这个应用是个人学习用途，但若要商用，中文这一条需要换成许可更宽的语音
- **句间停顿靠前瞻合成压掉，能压到多少取决于设备算力**：神经语音合成一句要 0.3–30 秒（视句长与音色），早期版本把合成和播放放在同一个线程上，这段等待就成了两句之间那段可听见的空白。现在合成与播放各占一个线程，开始朗读某句时同时向后多看几句，代价是朗读时多占一个 CPU 线程与几段音频的内存（`NeuralTts` 的预取台账按角色分两个上限：留存几段成品音频=内存上限，队列里最多排多少=吞吐上限）。读者自己在等的那句会**越过**排在它前面的前瞻任务：引擎是单线程 FIFO，`generate` 一旦开始就无法中断，所以"谁先合成"只在尚未开始的任务之间可选。

  这条前后被量错过两次，记下来免得下次又猜。条件固定为 4 核 x86_64 模拟器、朗读译文关闭、同一篇 16 句文章、同一爱登堡克隆音色：

  | 版本 | 句间静音合计 | >0.4 秒的停顿 | 最长一次 | 引擎忙碌占比 |
  | --- | --- | --- | --- | --- |
  | 双上限（留存 2 / 队列 4），只后看 2 句 | 93.9 s | 6 次 | 30.6 s | 未测 |
  | 再加上"让路即放弃" | 56.6 s | 6 次 | 19.6 s | 71.5%（空闲 61.6 s） |
  | 让路改为"排到队尾"、后看 4 句 | 21.7 / 23.5 s | 4 次 | 13.5 / 14.0 s | 95.7%（空闲 7.2 s） |
  | 留存 4 / 队列 8，跳跃时清空台账（现行） | 19.7 s | 2 次 | 14.0 s | 95.3%（空闲 7.8 s） |

  两处根因都是**排队顺序**，不是算力：一是读者正在等的那句明明已经建好（16 句里 15 句命中前瞻），却要等队列里另一句更靠后的前瞻合成完才轮到它——这种倒置占了全部静音的 46%；二是只后看两句时引擎有大量时间没活干，整段朗读里空闲 61.6 秒，而读者同时等了 56.6 秒，把后看深度提到 4 句后空闲降到 7.8 秒。剩下的 19.7 秒里，15 个句间间隔有 13 个 ≤ 0.09 秒（只有第 1 句是 MISS，即首句现场合成），仅有的两段停顿（14.0 s、4.7 s）都在开头 40 秒内：引擎要在开头 11 秒的播放时间里先建好前三句共 32 秒的合成量，这个亏空属于冷启动，设备越慢越明显。日志显示第一个合成请求之前引擎还空转约 10 秒（会话初始化），把这段时间用来预合成还能再缩短开头那一段。

  前瞻还要在**读者跳跃**时整个丢掉（`discardLookAhead`）：点了"下一句"、跳读或换句之后，已缓存的音频对应的是被跳过的那几句，它们既永远不会被取用、也不会被"丢最新"的裁剪规则清掉，于是每个留存位都被占死，之后每段新音频一完成就被丢弃——前瞻会无声地失效，停顿重新变成每句一次。另外引擎任务若已开始合成就无法中断，所以"读者优先"只在尚未开始的任务之间生效；日志里的 `queuedMs`（读者这句在队列里等了多久）与 `deferred`（前瞻让路几次）就是用来分开这两种情形的
- **爱登堡音色是克隆，Narrator 不是**：见上文"朗读语音"。爱登堡那一条是 ZipVoice 用本人录音做零样本克隆，声音确实是他；Narrator 那一条是按基频、语速与停顿从 VCTK 里测出来的语域，不是某位解说员的克隆
- **句子译文需要网络**：词库与内置选段是离线的，但任意外刊文章的译文要走在线翻译服务。译文按段落整篇发送、取回后存在本机，同一篇不会重复请求；没有网络时英文正文照常可读，只在顶部提示重试
- **逐句对照靠机器翻译的句子边界**：译文是按段落获取的，要拆成逐句显示就得自己找出中文的句界。句数与英文一致时（真书语料里约六成段落）直接按标点切；不一致时按各句在整段中的篇幅占比，把中文的子句分配给对应的英文句子——机器翻译常把两句并成一句、或在一句里断成两句，硬按句号数对齐会有近四成段落退化成整段显示。分配结果若某句拿到的中文篇幅与它自己的篇幅相差过大（说明译文是改写而非重断句），仍退回整段译文——把半句中文摆到另一句英文下面，比不逐句更糟。两种显示都不影响英文正文与划词。分配本身是猜测，切在中文句子内部时尤其如此：句号处的边界来自翻译引擎，逗号处的边界来自篇幅比例
- 翻译走的是公开接口（Google 优先、MyMemory 兜底），受对方限流与可用性影响；MyMemory 单次上限 500 字符，长段落会拆句发送，因此兜底路径明显更慢
- **后台朗读是前台服务**：切到别的应用或锁屏时朗读继续，通知栏与锁屏各有一张播放控制卡（暂停/继续/停止）。Android 13 起第一次朗读会要通知权限，不给也能听，只是没有那张卡；锁屏控制需要系统把应用的通知设为可见。朗读会一直占用音频焦点与一个前台服务，直到按停止或退出阅读器
- **阅读进度按段落记，不按滚动像素**：退出时记下当前段落，再进来滚回那一段；同一段在屏幕上移动不会触发写入。进度只在本机，重装或换机由"备份与恢复"带过去（备份含生词本与阅读记录，不含正文与语音）
- **全文查找是扫描而不是索引**：每次查询都把书里每一章的正文读一遍再逐段匹配，命中上限 120 条。一本《傲慢与偏见》规模的书（127 千词）单次扫描约 10 毫秒，但代价随正文体积线性增长，几 MB 的纯文本书会到几百毫秒。查询在 IO 线程上、有 220 毫秒防抖、结果超过上限就提前停，所以不会卡界面，但大书上会看到转圈。做倒排索引要维护一份随导入/删除同步的额外结构，这个应用的书量不值得
- 部分外刊有付费墙或纯 JS 渲染，抓取失败时退回 RSS 摘要（短文仍可精读）
- 直播类文章（标题带 `– live`）由大量短段落拼成，篇幅可达数千词，段落之间不连贯；建议优先选普通报道
- 语法拆解是规则引擎而非统计句法分析器：用于定位主干与从句边界，歧义句仍需结合上下文判断。缩写会按展开形式还原（`We're expecting` → 主语 `We` + 谓语 `are expecting`），但 `'s` 只在代词与 `there`/`that` 之后当作 `is`，名词后的 `'s` 一律按所有格处理
- **个人生词率的分母是"要学的词"而不是全文词数**：只统计实词、排除功能词与句中首字母大写的专有名词，所以"生词 32/33（96%）"意思是 33 个值得学的词里有 32 个不认识，不是全篇 96% 的词都不认识。低于 20 个实词的短篇不出这个数字
- 阅读速度是估算：词数按每篇读到的位置算，停下的那一屏不计入，跳读会让数字偏高；看两周之间的趋势比看绝对值有意义
- 生词本的"已掌握/答对过"只按本机记录判断，换设备或清数据后需要重新积累；设置页的"备份与恢复"可以把生词本与阅读记录导出成 JSON 带到新设备
- 理解题为自动生成，考察词汇与指代，不覆盖全文主旨理解
- **导入的书只保留文字**：插图、表格与排版样式都不会进入正文，一本书导入后就是"章节 + 段落"。这是刻意的——正文进的是 `article` 表，阅读器只认识段落，把图片接进来等于为书再写一套渲染
- **加密书（DRM）会被拒绝**：MOBI 的 `encryptionType` 非 0、或 EPUB 带加密清单，都会明确提示而不是解出乱码
- **导入是本机行为**：解析在设备上完成，不联网、不上传；但一本书按章节全量入库，几十 MB 的书导入要几秒到几十秒，期间界面会显示正在导入
